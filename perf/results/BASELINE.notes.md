개선 작업 전 bidder의 성능 기준선이다. 이후 개선 결과는 이 문서와 같은 조건·같은 스크립트로 측정해 비교한다.

## 시나리오 구분

| 시나리오 | 성격 | 질문 | 판정 | 이 문서 |
|---|---|---|---|:---:|
| **A** | 동시성 정합성 검증 | 동시에 몰려도 예산이 정확한가 | 통과/실패 | 포함 |
| **B** | 처리 용량·병목 측정 | 어디까지 SLA를 지키고, 무엇이 한계를 정하는가 | 수치 (최대 처리량, p99) | 포함 |
| **C** | 과부하·장애 내성 (신뢰성) | 한계를 넘거나 장애가 나도 버티고 회복하는가 | 수치 + 통과/실패 | 미측정 |

- A는 성능이 아니라 정확성을 본다. 2,000 req/s 조건처럼 bidder가 포화된 상태에서도 판정 대상은 정합성이다.
- B는 정상 부하에서 출발해 한계 지점까지 올라가며 용량과 병목을 측정한다. 한계를 넘은 단계의 붕괴는 부수적으로 관찰한 것이며, 포화가 감지되면 이후 단계를 생략하므로 과부하를 체계적으로 평가하지 않는다.
- C는 아직 측정하지 않았다. 지속적인 초과 부하에서의 동작(부하 차단, 회복), 장애 주입(bidder 재시작 중 만료 알림 유실, Redis 재시작)이 여기에 속한다. B에서 관찰된 붕괴가 C가 필요한 근거다.

## 기준값

### 시나리오 B (처리 용량·병목 측정): 캠페인 수별 처리 한계

| 캠페인 수 | 기준 처리량 (3/3 통과) | 경계 (일부 회차만 통과) | 포화 | 요청 1건당 Lettuce I/O 스레드 CPU |
|---:|---:|---:|---:|---:|
| 10 | **1,000 req/s** | - (1,500은 0/3) | 2,000 | 0.51 ms |
| 100 | **250 req/s** | 300 (2/3) | 350 | 3.1 ms |
| 1,000 | **25 req/s** | 30 (1/3) | 30~40 | 32 ms |

- 기준 처리량은 **모든 회차에서 p99 ≤ 100ms를 통과한 가장 높은 요청률**이다. 회차별 최대값의 중앙값보다 보수적인 값으로, 개선 전후 비교에는 이 값을 쓴다.
- 요청 1건당 Lettuce I/O 스레드 CPU는 해당 스레드 사용 코어를 요청률로 나눈 값이다 (c10: 0.51코어 / 1,000 req/s).

### 시나리오 A (동시성 정합성 검증): 예산 정합성

| 조건 | 결과 |
|---|---|
| 500 req/s × 20s, 예산 100회 (경합 약 0.2초) | 3/3 통과 |
| 500 req/s × 20s, 예산 5,000회 (경합 약 10초) | 3/3 통과 |
| 2,000 req/s × 20s, 예산 20,000회 (bidder 포화 상태) | 3/3 통과 |

모든 회차에서 초과 예약 0건, 최종 잔액 = 초기 예산 − 확정 금액, 만료 후 남은 예약 키 0개.

## 시나리오 A: 동시성 정합성 검증

### 목적

입찰 요청이 동시에 몰려도 Redis Lua 기반 예약·확정·환불이 예산을 정확히 지키는지 검증한다. 성능이 아니라 **정합성**이 판정 대상이며, 결과는 통과/실패로 나뉜다. 장애를 일부러 일으키지 않았으므로 신뢰성(장애 시 동작)은 이 시나리오의 범위가 아니다.

### 방법

1. 캠페인 1개를 작은 예산으로 시드한다(1회 예약액 1원, 용량 = 예산 ÷ 1원).
2. 예약 TTL(30초)보다 짧은 20초 동안, 예산 용량보다 훨씬 많은 입찰을 고정 요청률로 보낸다. 부하 시간이 TTL보다 짧아야 만료 환불된 예산이 다시 쓰이지 않아 "성공 입찰 수 ≤ 용량"으로 판정할 수 있다.
3. 성공한 입찰의 절반에 win을 호출해 **확정 경로**와 **만료 환불 경로**를 함께 태운다.
4. TTL이 지나 예약이 모두 정리될 때까지 기다린 뒤 Redis 잔액·예약 키를 확인한다(`verify_budget.sh`).

판정 항목: ① 성공 입찰 수 ≤ 용량 ② `budget_reserved == 0` ③ 남은 `reservation:*`·`reservation_backup:*` 키 0개 ④ `budget_total ≥ 0` ⑤ `budget_total == 초기 예산 − win 수 × 1회 예약액`

### 확인한 것

| 조건 | 입찰 요청 | 예약 성공 | 확정 | 만료 환불 | 정리 시간* | 결과 |
|---|---:|---:|---:|---:|---:|:---:|
| 500 req/s, 용량 100 | 30,003 | 300 | 154 | 146 | 12~13초 | 3/3 |
| 500 req/s, 용량 5,000 | 30,002 | 15,000 | 7,545 | 7,455 | 23~25초 | 3/3 |
| 2,000 req/s, 용량 20,000 | 98,393 | 60,000 | 30,009 | 29,991 | 28초 | 3/3 |

\* 정리 시간: 부하 종료부터 예약이 모두 확정·환불될 때까지. 3회 합계.

1. **초과 예약이 한 건도 없다.** 9회 모두 예약 성공 수가 용량과 정확히 같았다(예산을 남김없이, 넘치지 않게 소진).
2. **경합 시간과 부하 수준에 관계없이 같은 결과다.** 경합이 0.2초뿐인 조건(용량 100)과 10초 이상 이어지는 조건(용량 5,000·20,000), bidder가 포화돼 요청이 1초 이상 대기열에 머무는 조건(2,000 req/s, p50 1.1~1.3초, 드롭 6,500~7,500건)에서 모두 통과했다. Lua 스크립트가 잔액 확인·차감·예약 기록을 한 번에 실행하므로 요청 처리 순서나 지연과 무관하게 정합성이 유지된다.
3. **확정과 환불이 정확히 나뉜다.** 9회 합계 예약 75,300건 중 확정 37,708건, 만료 환불 37,592건이며, 모든 회차에서 `최종 잔액 = 초기 예산 − 확정 금액`이 일치했다. 확정된 예약이 환불되거나 환불이 두 번 일어난 경우가 없다.
4. **만료 환불 누락이 없다.** 모든 회차에서 `reservation_backup:*` 키가 0개로 정리됐다. 다만 이는 bidder가 계속 살아 있어 키 만료 알림을 놓치지 않은 조건에서의 결과다(아래 "확인하지 못한 것").
5. **만료 알림은 TTL보다 수 초 늦게 처리된다.** 마지막 예약 생성 시각에서 역산하면 환불 완료는 TTL(30초) 뒤 약 2~3초(만료가 적을 때) ~ 약 6초(약 2만 건이 몰려 만료될 때)다. Redis가 만료 키를 주기적 샘플링으로 지우기 때문으로, 만료가 몰릴수록 늘어난다. 이 시간 동안 해당 예산은 다른 입찰에 쓰이지 못한다.
6. **이벤트 저장 건수도 일치한다.** 9회 모두 `bidding_log` 행 수 = 예약 성공 수, `win_log` 행 수 = 확정 수였다. 장애가 없는 조건에서 Kafka → log-consumer 경로의 유실은 없었다.

### 확인하지 못한 것

- **bidder 인스턴스 여러 대.** 단일 인스턴스에서만 검증했다. Lua 원자성은 Redis 안에서 보장되므로 예약 정합성은 유지될 것으로 보이나, 여러 인스턴스가 같은 만료 알림을 동시에 받는 경우는 측정하지 않았다(환불 스크립트가 백업 키를 지우므로 중복 환불은 막히도록 작성돼 있다).
- **만료 알림 유실.** 알림을 받는 bidder가 모두 내려가 있는 동안 만료된 예약은 환불되지 않고 `budget_reserved`에 묶인다. 이 장애는 유도하지 않았다.
- **낙찰가(clearing price) 과금.** 확정 시 입찰가를 그대로 차감한다. 낙찰가를 반영하는 로직이 없으므로 과금 정확성은 검증 대상이 아니다.
- **Redis 재시작·장애 조치, Redis Cluster.** 단일 Redis 인스턴스에서만 측정했다.

위 항목 중 만료 알림 유실, Redis 재시작은 장애 주입이 필요한 신뢰성 검증으로 시나리오 C의 범위다.

## 시나리오 B: 처리 용량·병목 측정

### 목적

입찰 경로가 p99 ≤ 100ms를 지키는 처리 용량을 찾고, 그 용량이 활성 캠페인 수에 따라 어떻게 변하는지, 무엇이 용량을 제한하는지(병목)를 측정으로 특정한다. 정상 부하에서 한계 지점까지를 측정 범위로 하며, 한계를 넘은 뒤의 동작 평가는 시나리오 C의 범위다.

### 방법

1. 캠페인 N개(10/100/1,000)를 모두 입찰 후보가 되도록 시드하고, 예산은 측정 중 소진되지 않게 크게 잡는다. 모든 입찰이 예약 성공 경로를 탄다.
2. 요청률을 단계별로 올리며 단계마다 60초씩 측정한다. 단계마다 Redis 통계를 초기화해 요청당 명령 수를 정확히 센다.
3. 단계마다 bidder CPU(docker stats), bidder 스레드별 CPU(`/proc`), Redis 명령 수·CPU·메모리를 함께 수집한다.
4. 같은 조건을 3회 반복하고, 모든 회차에서 p99 ≤ 100ms를 통과한 가장 높은 요청률을 기준값으로 삼는다.

### 확인한 것

**1. 요청 1건의 Redis 작업량은 `N + 10`개 명령, 네트워크 왕복 `N + 4`회다.**

c100 250 req/s 단계의 명령 구성(요청 15,001건)으로 분해하면 다음과 같다.

| 구분 | 명령 | 요청당 | 네트워크 왕복 |
|---|---|---:|:---:|
| 활성 캠페인 목록 | `SMEMBERS` | 1 | ○ |
| 캠페인 상세 | `HGETALL` | **N** (= 100) | ○ |
| 예산 예약 Lua | `EVALSHA` + 내부 `GET`·`DECRBY`·`INCRBY`·`HSET`×2·`EXPIRE` | 7 | ○ (1회) |
| 추적 정보 저장 | `HMSET`, `EXPIRE` | 2 | ○ (2회) |
| 만료 환불 Lua | `EVALSHA` + 내부 `HGET`×2·`DECRBY`·`INCRBY`·`DEL` | 6 × 환불 비율 | 리스너 측 |

요청당 실측 명령 수는 c10 약 21~24, c100 약 113, c1000 약 1,014로 `N + 10 + 환불분`과 맞는다. 추적 정보 저장이 `HMSET`과 `EXPIRE` 두 번의 왕복으로 나뉘어 있는 점도 확인됐다.

**2. 처리 한계는 캠페인 수에 반비례한다.**

| 캠페인 수 | 기준 처리량 | 낮은 부하 p50 | 요청당 Lettuce 스레드 CPU |
|---:|---:|---:|---:|
| 10 | 1,000 req/s | 약 1 ms | 0.51 ms |
| 100 | 250 req/s | 약 3.7 ms | 3.1 ms |
| 1,000 | 25 req/s | 약 34~38 ms | 32 ms |

요청당 Lettuce 스레드 CPU는 `0.2ms + N × 0.032ms`로 근사된다. 캠페인 1,000개에서는 부하가 거의 없어도 p50이 34ms로, RTB 응답 제한(100ms)의 3분의 1을 캠페인 조회에 쓴다.

**3. 병목은 Redis가 아니라 bidder의 Lettuce I/O 스레드 하나다.**

- 기준 처리량 부근에서 bidder CPU의 대부분을 Lettuce 이벤트 루프 **한 스레드**가 쓴다: c100 250 req/s에서 0.78코어(bidder 스레드 합계의 약 87%), c1000 25 req/s에서 0.80코어(약 92%).
- 같은 시점 Redis CPU는 c100 0.17코어, c1000 0.30코어로 여유가 있다.
- 원인: 공유 Redis 연결의 응답은 Lettuce 이벤트 루프 한 스레드가 처리하고, `CampaignAdapter`의 조회 체인에 스레드 전환(`publishOn`)이 없어 응답 해석·`collectMap`·도메인 변환(`LocalDateTime.parse`, 요청마다 생성하는 `DateTimeFormatter`)·정렬이 모두 그 스레드에서 실행된다.
- 결과: bidder에 2 vCPU를 할당해도 **실질 처리 능력은 1코어**로 제한된다. 포화 시점 bidder 전체 CPU가 200%에 닿기 전에 지연이 급증한다.

**4. 측정 전에 한계를 예측할 수 있었고, 예측이 맞았다.**

요청당 Lettuce 스레드 CPU(c100 3.1ms)로 계산한 이론 한계는 1초 ÷ 3.1ms ≈ 320 req/s다. 실제로 300 req/s에서 해당 스레드가 0.93코어에 도달해 SLA 경계(3회 중 2회 통과, p99 16~149ms)가 됐고 350 req/s에서 3회 모두 포화됐다. c1000도 이론 한계 약 30 req/s에 대해 25 통과(3/3), 30 경계(1/3)로 일치했다.

**5. 한계를 넘으면 무너진다.**

| 조건 | 목표 | 실제 처리 | p50 | 상태 |
|---|---:|---:|---:|---|
| c100 | 350 req/s | 234 req/s | 4.4초 | 대기열 누적, Lettuce 스레드 0.71코어 |
| c1000 | 40 req/s | 14 req/s | 13.5초 | 힙 고갈, GC 스레드가 CPU 대부분 사용, `OutOfMemoryError` 후 응답 불능 |

요청 타임아웃·부하 차단·대기열 상한이 없어, 처리하지 못한 요청이 대기열과 힙에 계속 쌓인다. RTB 거래소는 100ms 뒤 응답을 포기하지만 bidder는 버려진 요청까지 끝까지 처리한다. 또한 콜드 상태 JVM에 처리 한계 근처 부하(c10, 1,500 req/s)를 바로 주면 JIT 컴파일 전 쌓인 대기열이 워밍업 이후에도 해소되지 않았다(무효 측정으로 폐기, 원인 파악 후 워밍업 요청률 상한 250 req/s 도입).

**6. c10의 한계는 부하 급증 흡수 능력이 정한다.**

1,500 req/s 단계는 3회 모두 단계 시작 직후 bidder CPU가 190~210%로 순간 포화된 뒤 120~145%로 안정됐고, 이때 Lettuce 스레드는 0.74코어로 여유가 있었다. 1분 약 9만 건의 상위 1%는 단계 시작 1~2초의 지연 폭주만으로 채워진다. 부하를 250 → 500 → 750 → 1,000 → 1,500으로 천천히 올린 예비 측정에서는 1,500 req/s가 통과했다. c10의 기준값 1,000 req/s도 한 회차는 p99 86.5ms로 경계에 가깝다.

**7. N+1 조회를 없애면 다음 병목이 될 비용이 c10에서 보인다.**

c10 1,500 req/s의 스레드별 CPU: Lettuce 0.77코어, HTTP 처리(`reactor-http-nio`) 0.18코어, Kafka 프로듀서 0.13코어, 로그 출력(`AsyncAppender`) 0.04코어. 캠페인 조회 비용이 사라지면 HTTP 처리, Kafka 직렬화·발행, 메시지마다 남기는 INFO 로그의 비중이 커진다.

### 확인하지 못한 것

- **win·노출·클릭 경로의 성능.** 입찰 경로만 측정했다(`WIN_RATIO=0`).
- **인스턴스 수평 확장.** 단일 bidder 인스턴스 기준이다.
- **타겟 필터링이 있는 현실적인 캠페인 분포.** 모든 캠페인이 후보가 되는 최악 조건만 측정했다.
- **장시간 운영.** 단계당 60초, 회차당 약 7분이라 시간에 따라 누적되는 자원(아래 Redis 메모리)은 드러나지 않았다.
- **과부하 지속 시 동작과 회복.** 포화 이후 단계는 생략했고, 포화 단계도 c1000 40 req/s처럼 일부 회차만 측정됐다. 체계적인 과부하 평가는 시나리오 C의 범위다.

## 측정 과정에서 발견한 문제

측정 준비와 결과 분석 중에 발견했고, 기준선 수치와 별개로 개선 대상이다.

| 문제 | 근거 | 영향 |
|---|---|---|
| 만료 리스너가 메시지마다 새 스레드를 생성 | 로그의 스레드 이름 `redisMessageListenerContainer-154284` (한 회차에서 15만 개 이상 생성). Spring 기본 실행기 `SimpleAsyncTaskExecutor` 사용 | 환불 1건마다 스레드 생성 비용. 스레드별 CPU 측정에서도 누락된다 |
| 추적 정보가 Redis 메모리를 계속 점유 | `auction_tracking` TTL 1시간. 입찰 1건당 Redis 메모리 약 0.56KB 증가(c10 1,500 req/s 단계에서 9만 건에 50.8MiB) | 1,000 req/s가 1시간 지속되면 약 2GB로, 측정용 Redis 제한(512MiB)을 넘는다 |
| 과부하 보호 장치 없음 | 시나리오 B 확인한 것 5 (부수 관찰, 체계적 평가는 시나리오 C) | 한계를 넘는 순간 대기열·힙 고갈로 서버가 응답 불능 |

| win 응답이 확정 성공 여부와 무관하게 항상 204 | `WinController` | 확정 실패를 호출 측이나 모니터링에서 구분할 수 없다 |

## 측정 조건

| 항목 | 값 |
|---|---|
| 측정 대상 | bidder 이미지 `5a178209bea0` (앱 코드 커밋 `e86468a` 기준, 측정 중 재빌드 없음) |
| bidder 리소스 | 2 vCPU / 1 GiB, `-Xms512m -Xmx512m -XX:+UseG1GC` (`perf/docker-compose.perf.yml`) |
| 기타 서비스 | Redis 1 vCPU / 512 MiB, Kafka 2 vCPU / 1.5 GiB 등 (같은 파일) |
| 호스트 | Apple M3 Max 16코어, Docker Desktop VM 16 CPU / 7.6 GiB. k6는 같은 호스트에서 실행하며 Docker 포트 포워딩을 거친다 |
| 부하 | k6 `constant-arrival-rate`(요청률 고정, 개방형 모델). 단계별 60초, 단계 사이 10초 휴지 |
| 워밍업 | 캠페인 시드 후 60초, 요청률은 첫 단계와 250 req/s 중 작은 값 |
| 시드 | 캠페인 N개 모두 같은 CPM·같은 타겟(요청과 일치)으로 전부 입찰 후보가 되는 최악 조건. 예산은 측정 중 소진되지 않는 크기 |
| win 호출 | 없음(`WIN_RATIO=0`). 모든 예약은 30초 뒤 만료 환불되므로, 정상 상태에서는 입찰 1건마다 환불 1건이 함께 처리된다 |
| SLA 판정 | p99 ≤ 100ms, 드롭 < 1%, 에러 0 |
| 포화 판정 | p99 > 1초 또는 드롭 > 1%. 포화 이후 단계는 측정하지 않는다 |
| 고정 설정 | 트레이싱 샘플링 100%, Kafka 메시지마다 INFO 로그 (기준선의 일부) |

p99는 단계 전환 직후의 과도 구간을 포함한다. 갑작스러운 트래픽 증가를 흡수하는 능력까지 포함한 값이다.

## 개선 결과와 비교할 때의 규칙

1. **같은 RATES, 같은 시드 조건, 같은 `WIN_RATIO`로 3회 반복한다.** 비교 값은 "모든 회차 통과 최대 처리량"이다.
2. **이미지를 다시 빌드한다(`BUILD=1`).** `env.json`의 `images.bidder.created`가 `appSources.bidder.lastCommit`보다 뒤인지 확인한다.
3. **한 번에 하나만 바꾼다.** 트레이싱 비율, 로그 레벨, 리소스 제한처럼 기준선에 포함된 설정을 함께 바꾸면 효과를 구분할 수 없다. 바꿔야 한다면 별도 측정으로 분리한다.
4. **시나리오 A를 회귀 검사로 다시 돌린다.** 최소 `oversell-r500-b5000` 조건 3회.

## 알려진 한계

- 단일 호스트의 Docker Desktop 환경이다. 절대 지연 값에는 포트 포워딩 비용과 k6의 호스트 CPU 사용이 섞여 있어, 운영 환경 수치로 일반화하지 않는다. 같은 환경에서의 전후 비교 용도다.
- 스레드별 CPU는 측정 시작과 끝에 모두 살아 있는 스레드만 집계한다. 메시지마다 새로 생성되는 만료 리스너 스레드(`redisMessageListenerContainer-N`)처럼 수명이 짧은 스레드의 CPU는 빠진다. docker stats 기준 bidder CPU와 스레드 합계의 차이(c10 1,500 req/s에서 약 0.12코어)가 이 몫으로 추정된다.
- c1000의 40 req/s 단계는 3회 중 1회만 측정됐다. 나머지 두 회차는 30 req/s에서 포화돼 이후 단계를 생략했다.
- 시나리오 A의 콜드 스타트 회차(`oversell-r500-cold`)는 k6 요약 저장에 실패해 출력값으로 복원했다.
- `perf/results/latency-*`는 측정 방법을 확정하기 전의 예비 측정으로, 기준선에 포함하지 않는다.
